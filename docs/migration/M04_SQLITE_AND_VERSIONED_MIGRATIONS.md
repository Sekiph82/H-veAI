# M04 SQLite and Versioned Migrations

## Scope

M04 adds H!veAI-owned local persistence infrastructure only. It does not register projects, scan repositories, start the legacy Python runtime, or implement Project Registry workflows.

## Technology

The Rust native core uses `rusqlite` with its `bundled` feature. SQLite is embedded into the H!veAI desktop binary, so there is no external database service or Python dependency. Connections are initialized during Tauri startup and are migrated before the application reports a healthy persistence boundary.

## Location and safety

The production database is stored at:

`<Tauri app-data directory for ai.hiveai.desktop>\hiveai.db`

On Windows this resolves under the current user application-data location used by Tauri for the identifier `ai.hiveai.desktop` (for example, the local app-data tree). The exact absolute path is intentionally not exposed to the frontend; the read-only status command reports `hiveai.db` as an app-data-relative path.

The repository, parent `AI-Commerce-HQ` database, and user project folders are never used as the production database location. M04 tests create isolated temporary directories and do not call the production path resolver.

## Migration mechanism

`src-tauri/src/db/migrations.rs` contains an ordered migration list. Each migration has a positive contiguous version, human-readable name, and deterministic SQL. The `migrations` table records version, name, and UTC applied timestamp. Each migration runs in its own SQLite transaction. A SQL error rolls that migration back and is returned to Tauri startup; the application does not silently continue.

Startup is idempotent: an already-current database records `ALREADY_CURRENT` and is not changed. Unknown, missing, reordered, or name-mismatched migration history fails safely.

Current schema version: **2**.

## Schema overview

Migration 1 creates:

- Project layer: `projects`, `repositories`, `project_sources`, `git_snapshots`
- Task layer: `tasks`, `task_dependencies`, `task_sources`, `task_events`
- Prompt and agent layer: `prompts`, `prompt_versions`, `agent_sessions`, `agent_events`, `agent_tool_calls`, `permission_requests`
- Audit and testing layer: `audits`, `audit_findings`, `test_runs`
- Coordination layer: `alerts`, `decisions`, `github_sync_state`, `settings`
- Migration history: `migrations`

Migration 2 adds explicit lookup indexes for project/task state, source discovery, snapshots, task dependencies/events, prompt versions, agent activity, permissions, audits/findings, test runs, alerts, decisions, GitHub synchronization, and settings scope.

Identifiers are durable text IDs. Timestamps are UTC ISO-8601 strings generated by the database for migration history; domain records use the same documented UTC convention. Filesystem paths and GitHub URLs are data fields, never primary keys.

Foreign keys are enabled explicitly for every connection. Relationships include project-owned repositories and tasks, task dependencies, prompt versions, agent events/tool calls, audit findings, and coordination records.

## Status IPC and startup order

The narrow `hiveai_database_status` command reports initialized state, engine, schema version, migration count, sanitized database path, foreign-key status, and last migration status. It does not expose SQL execution or arbitrary paths.

Tauri startup order is:

1. Resolve the Tauri app-data directory.
2. Create the H!veAI-owned directory if needed.
3. Open `hiveai.db`.
4. Enable foreign keys.
5. Apply migrations.
6. Register database status.
7. Continue application startup only after success.

The existing M03 runtime supervisor remains Rust-native and no legacy sidecar is started.

## Failure, backup and recovery

Migration failures return a clear startup error. The failing transaction is rolled back, while previously committed migration versions remain inspectable. The database file is not automatically deleted or replaced. Future backup/restore flows must be permission-gated, preserve the migration history, and validate the restored schema before activation.

## Privacy and security

No tokens, passwords, private keys, `.env` contents, raw credentials, or arbitrary SQL are persisted or exposed. JSON columns are for structured non-secret metadata only. Tauri capabilities allow only the read-only database status command in addition to existing M01/M03 commands.

## M05 boundary and limitations

M05 may use these tables to implement a read-only project registry and path validation workflow. M04 does not automatically open, scan, normalize, mutate, or register repositories, and it does not populate production records. Connection pooling, backup UI, encryption at rest, and production CSP tightening remain future hardening work.
