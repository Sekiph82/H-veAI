## 4. BUILDER CLAIMS VS REPOSITORY TRUTH

### Claim: watcher blocker is fully closed

The log says ordinary refreshes preserve overflow evidence and explicit successful rescan is the only clearing transition.

Repository truth is narrower. `refresh_project_snapshot` clears `status.rescan_required` whenever `explicit` is true, including when the project is unavailable. `rescan_project` can call this path for a missing project and return a `MISSING` status without treating the reconciliation as failed.

The persisted snapshot is written before the in-memory explicit clear. For a missing explicit rescan, the persisted row can record `rescan_required=1` while in-memory status becomes `false`, violating the prompt's required persistence/in-memory agreement.

### Claim: M07 focused evidence gaps are closed

They are not. The source contains useful new tests for lexical outside-root rejection and ordinary-refresh rescan preservation, but required focused tests are still missing for multiple contract items including:

- positive rename normalization
- duplicate watcher prevention
- repaired-path reattachment
- Git-category watcher event -> persisted Git snapshot integration
- startup with one missing project remains safely degraded
- clean shutdown proves watcher resources are released
- explicit no-arbitrary-path IPC evidence
- failed explicit rescan preserves required state

### Claim: binary diff is metadata-only

Production `diff()` no longer requests `--binary`, which is a useful correction. However, the test named `binary_diff_is_metadata_only` invokes raw `git diff --binary` directly and does not exercise the H!veAI `diff()` boundary. It accepts either `Binary files` or `GIT binary patch` text and therefore does not prove the required guarantee.

The production parser still contains a `raw.contains("GIT binary patch")` branch but does not strip such a section before returning `raw` through `bound_text`. The required deterministic guarantee is therefore not implemented defensively.

### Claim: canonical timestamp migration is complete

New timestamp generation now uses RFC3339 UTC milliseconds through `crate::time::utc_timestamp()`.

Migration 5 converts several historical epoch-text fields, but does not convert `project_snapshots.created_at`, which was populated by M07 using the old epoch-string timestamp function. Therefore backward compatibility is incomplete for a known M07 table.

The prompt-required tests for RFC3339 shape, ordering, epoch migration, and malformed legacy values are also absent from the inspected migration tests.

### Claim: Project Registry repair identity is hardened

Git identity comparison improved, but a major fail-open path remains. Non-Git registrations do not create a `repositories` row. `repair_project_path` reads identity only from `repositories`; when no row exists, `existing_identity=None` and all type/remote/HEAD checks are skipped. A registered non-Git project can therefore silently repair to an unrelated Git project, directly violating Part D.

Additionally, for Git projects with matching remotes, any HEAD difference is rejected even when repository identity is otherwise strong. This is too rigid for a moved repository that legitimately advanced commits and does not implement the requested evidence/ancestry decision matrix.

No direct repair-identity focused tests were added.

### Claim: SQLite backup is safe/atomic

Connection hardening is useful, but `create_migration_backup` uses `fs::copy(database_path, temporary)` on the main SQLite file after WAL mode is configured. A WAL-mode database can have committed data in the WAL file that is not represented in a raw main-file copy. This is not a SQLite-consistent backup mechanism.

The required lock/busy behavior test is absent. Corruption classification/recovery is not exercised by a focused corruption test. Repeated replacement of an existing pre-migration backup is also not directly tested.

### Claim: required blockers/majors are closed

This claim is false under the strict audit contract. The historical M07.01 log must remain immutable, but a new remediation log/document must correct the record.
