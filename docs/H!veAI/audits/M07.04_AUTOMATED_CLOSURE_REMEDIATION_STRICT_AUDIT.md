# Gate 1 — Functional Gate: FAIL

## F01 — BLOCKER — Ordinary watcher refresh can still clear `rescan_required`

File:

`H!veAI/src-tauri/src/watcher.rs`

Current production code computes:

```rust
let successful_reconciliation = available && (explicit || !events.is_empty());
let rescan_required = if successful_reconciliation {
    false
} else {
    prior_rescan_required
};
```

This is incorrect. A normal watcher event refresh with `explicit == false`, a non-empty event list, and `prior_rescan_required == true` is treated as successful reconciliation and clears the recovery flag.

The M07.04 prompt explicitly requires ordinary refresh to **never** clear a required rescan.

Current test `ordinary_refresh_preserves_overflow_until_explicit_rescan` uses `Vec::new()` for the ordinary refresh, so it does not exercise the failing non-empty event path.

Required correction:

- only a successful **explicit** reconciliation may clear `rescan_required`;
- normal event refresh must preserve prior true state regardless of event count;
- add a direct production-path regression test using a non-empty normalized event vector.

## F02 — BLOCKER — Explicit rescan does not prove watcher attachment/reconciliation success

`WatcherManager::rescan_project()` calls `configure_project()` and then `refresh_project_snapshot(..., explicit=true)`.

`configure_project()` currently converts watcher creation/watch failures into `Ok(())` after setting an in-memory degraded status. `refresh_project_snapshot()` then defines reconciliation success primarily from filesystem availability. Therefore an available project whose native watcher failed to attach can still be treated as successfully reconciled and have its rescan flag cleared.

Required correction:

- watcher configuration must return a meaningful attachment/reconciliation outcome or error;
- explicit recovery must not clear until required watcher/Git/persistence steps all succeed;
- available-but-unwatchable must remain degraded/rescan-required when recovery was required.

## F03 — MAJOR — Registry repair does not reattach an existing watcher to a repaired path

`configure_project()` returns early whenever `inner.watches.contains_key(&project.id)` is true. The watch map does not track the root path that the watcher is attached to.

After Project Registry path repair, a registry refresh for the same project ID can therefore keep the existing watcher bound to the old root instead of replacing it with a watcher on the repaired root.

This violates the required repaired-path reattachment test/behavior.

Required correction:

- track the configured root for each project watcher;
- if the registered normalized root changes, drop the old watcher and attach a new one to the new root;
- directly test repair -> watcher refresh -> event on new root.

## F04 — BLOCKER — Legacy non-Git registrations can still bypass type-change protection

M07.04 changed `insert_repository()` so **new** non-Git registrations now receive a `repositories` row with `is_git_repository = 0`.

However, projects registered before this change can legitimately have no repository row. `repair_project_path()` still reads identity only from `repositories`; if the row is absent, `existing_identity == None` and the type decision matrix is skipped.

Therefore an M07.03-or-earlier legacy non-Git registration can still be repaired to an unrelated Git repository without the mandatory non-Git -> Git rejection.

Required correction:

- for an existing registered project with no repository row, treat that historical state as durable legacy non-Git identity, or migrate/backfill safely;
- do not fail open on `existing_identity == None`;
- add a direct legacy fixture: registered project row with no repository row -> Git repair must reject.

## F05 — MAJOR — Binary metadata detection remains non-deterministic for added/staged binary files

`GitDiff.binary_files` is still primarily parsed from human-readable `git diff` text via `Binary files ... and ... differ`.

For newly-added staged binary files Git can use `/dev/null` as one side of the textual diff header. Parsing the first side can therefore produce `/dev/null` instead of the actual repository-relative binary path.

The prompt specifically called for deterministic metadata detection and suggested bounded `--numstat` binary classification.

Required correction:

- use a separate safe metadata command such as matching-scope `git diff --numstat` and classify `-\t-` rows as binary;
- keep textual diff and binary metadata concerns separate;
- add actual `diff(database, request)` tests for staged new binary, working-tree binary, and mixed text+binary.

# Gate 2 — Specification Gate: FAIL

## S01 — MAJOR — Required watcher evidence matrix was not added

The M07.04 prompt requires production-path tests for rename normalization, outside-endpoint rename, duplicate watcher prevention, repaired-root reattachment, Git-category persisted snapshot refresh, non-Git watcher behavior, missing-project initialization, clean shutdown, IPC boundary, containment, and the full rescan state matrix.

The final watcher test suite still contains the earlier small set and does not provide this matrix.

## S02 — BLOCKER/MAJOR — Registry identity decision-matrix tests are absent

The prompt requires direct tests for:

- non-Git -> non-Git;
- non-Git -> Git reject;
- same remote/same HEAD;
- same remote/advanced HEAD;
- different remote;
- disappearing remote policy;
- no-remote exact HEAD;
- no-remote ancestor continuity;
- unrelated/missing history rejection;
- credential-bearing equivalent remotes;
- duplicate repair path;
- external repository unchanged;
- unknown project ID.

The final `registry.rs` test module still contains only three broad tests: registration/duplicate, archive/remove/repair folder safety, and list/search/missing state.

The required identity matrix is not present.

## S03 — MAJOR — Migration v7 exists, but the required migration test matrix is absent

Version 7 exists and updates `project_snapshots.created_at`, but the required v6 -> v7 historical fixture, valid RFC3339 preservation, malformed-value preservation, timestamp generator precision/order, and M05-M07 legacy sample coverage are not present.

Current tests mainly update expected schema/migration counts from 6 to 7.

## S04 — MAJOR — Applied migration v5 was retroactively modified

M07.04 added `project_snapshots.created_at` conversion into `TIMESTAMP_STANDARDIZATION` (migration 5) **and** added migration 7.

Because H!veAI migration history currently validates only `(version, name)` and not a SQL checksum, changing an already-published migration body creates historical drift: databases that already applied v5 and fresh databases now associate different SQL semantics with the same migration identity.

The correction should live in migration 7. Historical v5 should be restored to its previously published body.

Important compatibility rule for the next remediation:

- do **not** rename migration 7 or change its identity if it may already have been applied locally;
- keep version 7/name stable and restore historical v5 text instead.

## S05 — MAJOR — SQLite required durability tests remain absent

The production direction (`rusqlite::backup`, `.bak`/`.bak.prev`) is improved, but the prompt explicitly requires tests for:

- second/repeated backup;
- bounded retention;
- simulated publication failure;
- prior backup preservation on failure;
- busy/locked contention within bound;
- corrupt DB byte preservation;
- healthy quick-check;
- per-connection safety pragmas;
- migration abort-before-mutation when backup fails.

Only the earlier basic logical-backup test is present.

## S06 — MAJOR — Git diff tests still do not exercise the actual H!veAI `diff()` boundary

The renamed test `raw_binary_diff_fixture_is_sanitized_at_the_product_boundary` still executes raw `git diff --binary`, then calls `sanitize_binary_payloads()` directly.

It does **not** create a registered project/database and call:

```rust
diff(database, GitDiffRequest { ... })
```

The prompt explicitly requires the real product-boundary matrix for text, staged, binary, mixed, sanitizer fallback, and post-sanitation truncation.

## S07 — MAJOR — Launcher rollback/failure-path test harness is absent

The publisher now removes `-SkipBuild`, always runs Tauri `--no-bundle`, performs candidate smoke, and smoke-tests the final stable path. Those are real improvements.

However R09 explicitly requires safe temp-path controlled failure tests for invalid PE, provenance/readiness failure, shortcut/icon failure, post-swap failure, locked stable file, candidate cleanup, successful publication, and final hash equality.

No launcher test harness was added in the M07.04 commit.

## S08 — MAJOR — Rollback hash verification is not implemented

R09 requires that a post-publication failure restore the previous stable executable **byte-for-byte** and verify the restored hash equals the pre-publication stable hash.

`publish-dev-qa.ps1` moves the prior stable file to `H!veAI.rollback.exe` and moves it back on failure, but it does not record or verify a pre/post SHA-256 hash.

- emit `HIVEAI_FRONTEND_READY` only from the dedicated readiness command;
- ensure the command is explicitly covered by the intended Tauri permission/capability policy;
- keep the publisher baseline-offset logic.

This is not the primary reason for FAIL, but it should be cleaned up in the bounded next pass.
