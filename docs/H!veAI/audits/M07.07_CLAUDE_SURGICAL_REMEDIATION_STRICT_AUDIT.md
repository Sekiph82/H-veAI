## C. ACCEPTANCE MATRIX

### C01 SQLite corruption-safe preflight production implementation — PASS

`DatabaseState::initialize()` now:

1. detects an existing non-empty DB;
2. calls `integrity_preflight()` before opening/configuring the normal RW connection;
3. `integrity_preflight()` opens SQLite READ_ONLY and runs `PRAGMA quick_check(1)`;

This closes the M07.06 production ordering defect.

The corrupt-byte preservation test also exercises the production initializer and proves the fixture bytes remain unchanged after rejection.

### C02 SQLite durability failure-path evidence — FAIL / MAJOR

Three required tests are misleading or incomplete:

1. `sqlite_busy_locked_contention_respects_configured_bounds`
   - does not create two contending connections;
   - does not hold a transaction/lock;
   - does not attempt an operation expected to return BUSY/LOCKED;
   - only reads `PRAGMA busy_timeout` and asserts 5000.

2. `sqlite_backup_publication_failure_preserves_source_and_prior_backup`
   - does not induce backup publication failure;
   - performs two successful `create_migration_backup()` calls;
   - proves successful rotation/retention, not failure preservation.

3. `sqlite_backup_failure_prevents_migration_mutation`
   - creates `readonly_sub` but never routes backup publication through it;
   - does not inject or observe a backup failure;
   - accepts successful initialization and merely asserts migration version remains `>= 1`;
   - therefore does not prove migration v7/schema mutation is prevented when backup fails.

The M07.07 builder log claims these tests simulate actual failure conditions, including a read-only-directory publication failure. Repository source contradicts that claim.

### C03 Watcher evidence matrix — FAIL / MAJOR

Several newly named tests do not exercise the production failure/event claimed by their names:

- `watcher_attachment_failure_preserves_rescan_requirement` never invokes an attachment failure; it calls `refresh_project_snapshot(... explicit=false)` on a manually seeded degraded state.
- `watcher_git_refresh_failure_preserves_rescan_requirement` registers a normal non-Git temp folder, so the Git snapshot branch is not entered; no Git refresh failure is induced.
- `watcher_snapshot_persistence_failure_preserves_rescan_requirement` does not make snapshot persistence fail; the insert succeeds.
- `watcher_unchanged_refresh_does_not_duplicate_watcher` compares project-status count, not the actual watcher-handle/root count or identity.
- `watcher_repaired_root_refresh_reattaches_to_new_root` proves only that state remains `WATCHING`; it does not assert `watch_roots[project_id] == new_root` and old root is detached.
- `watcher_event_on_repaired_root_is_observed` writes a file and sleeps, then only asserts `status.available`; it does not prove an event timestamp/count/snapshot changed.
- `watcher_git_category_event_persists_snapshot` uses a non-Git registered folder and asserts `project_snapshots` count, not a `git_snapshots` row / non-null `git_snapshot_id`.
- `watcher_manager_drop_releases_worker_and_watchers` only calls `drop(manager)` and makes no post-drop assertion via retained shared state.
- `watcher_symlink_escape_rejected_by_physical_containment` does not create a symlink/junction at all; it compares an ordinary file inside root against an ordinary file outside root.

Positive source review still indicates the underlying watcher production logic is substantially stronger than earlier M07 iterations. This finding is specifically about required direct failure/lifecycle evidence.
