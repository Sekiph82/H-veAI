# H!veAI M07.02A Development QA Launcher Strict Audit

## VERDICT

**FAIL**

The immediate user-facing launcher defect is materially corrected, but the M07.02A contract is not fully closed because the durable publication helper does not yet enforce production-build provenance, candidate smoke-before-publication, or last-known-good rollback semantics. M07.02 remains open and M08 remains blocked.

## CONTRACT RECOVERY

M07.02A required all of the following:

- stable QA executable built through Tauri production mode (`tauri build --no-bundle` or equivalent), not a dev-mode/raw Cargo artifact that may depend on `build.devUrl`;
- no runtime Vite/localhost dependency;
- no visible console window during normal GUI launch;
- `Desktop\H!veAI.lnk` targeting the stable executable directly;
- canonical shortcut icon derived from `H!veAI small logo.png`;
- no installer;
- no legacy sidecar / no port 8765 listener;
- file/plugin logging retained;
- durable publication logic that validates the candidate with Vite stopped **before** replacing the previous known-good executable;
- previous known-good executable preserved if validation/publication fails;
- durable launcher documentation updated so future milestones cannot regress to the bad build path.

## BUILDER CLAIMS VS REPOSITORY TRUTH

### Claim: M07.02A blocker corrected and directly smoke-tested

**Supported for the currently published executable.**

The implementation adds the conventional Windows GUI-subsystem attribute and the log records a no-5173 direct/shortcut smoke. The user's subsequent screenshots show the H!veAI interface rendering successfully, which is stronger manual evidence than the earlier process-alive-only smoke.

### Claim: durable publication helper safely validates before replacement

**Only partially supported.**

The helper stages the candidate and checks that it is a non-empty Windows PE file, but PE validity is not equivalent to H!veAI production-build validity. It then replaces `dev-bin\H!veAI.exe` before validating shortcut/icon state. Therefore a later validation error can occur after the previous known-good executable has already been overwritten.

## FILE / SYMBOL EVIDENCE

### `src-tauri/src/main.rs`

The release-only Windows subsystem attribute is correct and appropriately scoped:

```rust
#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]
```

This closes the visible-console defect for release-mode QA builds while leaving debug builds observable.

### `scripts/publish-dev-qa.ps1`

The helper currently:

1. defaults to `src-tauri\target\release\hiveai-desktop.exe`;
2. copies to `H!veAI.exe.staged`;
3. validates only the `MZ` header/nonzero PE shape;
4. immediately replaces `H!veAI.exe`;
5. only afterward validates `.lnk` target and ICO location.

The script does **not**:

- run or require `npm run tauri:build -- --no-bundle` itself;
- prove the candidate was produced by Tauri production mode rather than raw `cargo build --release`;
- ensure port 5173 is stopped before candidate validation;
- launch the staged candidate and prove the embedded frontend renders before stable replacement;
- preserve/restore the previous stable executable if a post-replacement check fails.

These are direct contract gaps.

## FOCUSED TEST EVIDENCE

## DEFECTS BY SEVERITY

### BLOCKER — Publication provenance / pre-publication smoke is not enforced

A raw Cargo release executable can still be passed to the helper and accepted as long as it has an `MZ` header. This recreates the class of failure M07.02A was meant to prevent.

### MAJOR — Last-known-good rollback is not preserved

Stable executable replacement occurs before all validations and there is no rollback.

### BLOCKER — New user visual evidence: Command Center violates canonical single-viewport contract

This is not a M07.02A launcher regression, but it is a blocking cross-milestone UI finding that must be included in the next consolidated remediation prompt.
