# B02 — Fix the actual startup intro layout bug

## User-observed native behavior

On cold launch, for approximately the opening-video duration (~8 seconds):

- the dashboard is still visible;
- the window becomes larger/scrollable;
- horizontal and vertical scrollbars appear;
- the user can pan/scroll the temporary first state;
- after ~8 seconds, the temporary overflow disappears and the normal dashboard returns.

This is strong evidence that `StartupIntro` is mounting for the expected media duration but is not acting as a real overlay.

## Current source diagnosis

`StartupIntro.tsx` renders:

`<div className="startup-intro"> ... <video /> ... </div>`

as a sibling after `<App />`.

The current production stylesheet does not provide the required `.startup-intro` / `.startup-intro-closing` fixed-overlay treatment. Therefore the intro/video participates in normal layout flow after an app that already occupies the viewport, creating temporary document overflow. When `ended` removes the intro node, the scrollbars disappear.

Treat this as the primary visual root cause of the "video not visible" observation.

## Required fullscreen overlay CSS contract

Implement explicit production styles equivalent in behavior to:

```css
.startup-intro {
  position: fixed;
  inset: 0;
  width: 100vw;
  height: 100vh;
  z-index: 10000;
  display: flex;
  align-items: center;
  justify-content: center;
  overflow: hidden;
  background: #050914;
  opacity: 1;
  pointer-events: auto;
}

.startup-intro video {
  display: block;
  width: 100%;
  height: 100%;
  max-width: 100%;
  max-height: 100%;
  object-fit: contain;
  background: #050914;
}

.startup-intro-closing {
  opacity: 0;
  pointer-events: none;
}
```

Exact selectors/values may adapt to existing tokens, but the behavior is mandatory.

Additional requirements:

- the intro must cover the entire H!veAI client viewport;
- the dashboard may remain mounted behind it but must not be visually exposed while intro is active;
- intro/video must never add to document width/height;
- no horizontal scrollbar caused by intro;
- no vertical scrollbar caused by intro;
- no normal-flow margin/padding around the video;
- no browser chrome/player controls;
- no external media player, browser, terminal, or second Tauri window;
- `object-fit: contain` unless verified otherwise, because cropping the user's 16:9 composition is not allowed;
- black/deep-navy letterboxing is acceptable on non-16:9 windows;
- preserve natural `ended` event and short ~280 ms fade;
- media error/failsafe must dismiss safely;
- pre-React/background first paint remains dark to prevent bright flash.

Do not "fix" this by forcing body/app dimensions larger or hiding permanent app overflow globally in a way that masks unrelated layout bugs. The intro itself must be correctly removed from normal flow.

# B03 — Deterministic native-process intro ownership

Although the new native evidence shows the MP4 was likely mounted, startup/restart ownership must still be deterministic.

Required behavior:

- cold native launch => intro claim true, video plays exactly once;
- SPA navigation => no replay;
- project selection => no replay;
- minimize/restore => no replay;
- Settings -> Restart H!veAI -> confirmed native restart => new native lifecycle, video plays exactly once again;
- browser preview => no native claim and no startup video;
- App mounts immediately behind overlay;
- `hiveai_frontend_ready` remains independent of video completion.

Use a tiny native-process-scoped claim state rather than `sessionStorage` as lifecycle authority.

Preferred design:

1. process-local Rust state initialized fresh on Tauri startup;
2. dedicated command such as `hiveai_startup_intro_claim`;
3. first claim in process => `true`;
4. later claims in same process => `false`;
5. a new process after `app.request_restart()` receives fresh state and first claim => `true`;
6. do not persist the claim to SQLite, filesystem, Registry, localStorage, or sessionStorage.

`AtomicBool`, `Mutex<bool>`, or an equivalently tiny state is acceptable.

Follow current Tauri command governance:

- explicit registration;
- narrow permission/capability entry;
- no broad allow-all;
- no public bypass.

Frontend flow:

- native environment only requests the claim;
- while claim resolves, render the same fixed dark fullscreen overlay so no dashboard flash occurs;
- claim=true => play bundled MP4 inside the overlay;
- claim=false => dismiss overlay immediately;
- claim error => fail open to usable app;
- sessionStorage must no longer decide native lifecycle truth.

Do not change existing restart semantics except for minimum command/state registration required by this feature.
